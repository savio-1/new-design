User flow

The path depends on the workspace mode. In Off or Monitor a version goes live in one step. In Enforce it runs as a trial first and a second admin approves it. Numbers link to the screens below.

First rules1Rules · empty2Create rules4Starteror5Templateor6Write3Version + Publish
Off / Monitor1Rules · New version3Builder · Publish7Draft details8Make liveLive
Enforce3Publish and start trial7Trial · 48 h8ProposeSecond admin approvesLive
Undo7Was-live versionRoll back (confirm + reason)Live againIn Enforce only to a version approved for Enforce; otherwise start a trial.

How rules work (what the UI must protect)

A version is the whole rule set

Going live replaces the previous version; nothing is merged. The builder therefore always starts from the live rules (or the version chosen with “New version from this one”) and publishes all blocks as one cedar_text.

Every rule has a plain label

The builder writes @description("…") under each @id. The API returns it as rules[].description; the UI shows it everywhere instead of rule text.

Versions are never edited

Status is derived: Live (is_live), Trial (is_candidate), Was live (has been live), else Draft. Never trust is_live/is_candidate in publish or make-live responses; refetch the list.

Colour

Use tokens only, never hex values. The theme is switched by data-mode="light" on the root; dark is the default. Colour carries meaning in this flow: green allows or is live, red blocks or is an error, orange needs attention, indigo is a trial, blue is the action and selection colour.

Screens

Each specimen is the prototype’s real markup rendered with the production CSS. Overlays are frozen in place so they can be inspected.

1

Rules page

The live version in full, a one-line flow for the current mode, then all versions. Three states: populated, enforcing with a trial, and empty.

  • Heading: title Subhead2 18/24; description body 14/20 in --text-teritiary. Actions right: Test a call (32 icon button, bordered) + New version (primary, small).
  • Flow strip: “In Monitor:” label, then 28-tall pill steps, last step green. Enforce shows Publish → Trial 48 h → Approve → Live.
  • Live card: flush card; head 16 20 0; rules as flat rows divided by --strokes-line-3; open checks in a footer row.
  • Checks footer: one line per issue, icon 14 tinted by tone; the full sentence is in the title tooltip.
  • All versions: columns 1.4fr · 120 · 150 · 160 · 1.6fr · 40; row height 56; whole row opens the version drawer.
  • Status chips: Live light-green · Trial indigo · Was live grey with undo icon · Draft grey with edit icon.
2

Create rules

Shown whenever a workspace has no rules and the admin presses Create rules. Picking a path opens the builder directly on that path.

  • Modal 640 wide; header 56; body padding 16; lead 14/20 secondary.
  • Path rows: 40 icon well (blue starter · purple template · grey write), title 16/24 medium, caption 12/16 tertiary, chevron right.
  • Hover: border --strokes-card-selected, fill --backgrounds-table-select.
  • Starter rules carries a “Recommended” blue chip. No footer buttons: closing is the × or Esc.
3

Builder · the version

The home view of the builder: every rule in the version, then three ways to add one. The side pane holds checks, name and reason for the whole version.

  • Header: 28 icon well + “New rule version” 16/24 and a caption “Starts from …”.
  • Main pane padding 24, gap 24. Side pane 320, padding 24 20, fill --gv-nested, left border.
  • Rule row: effect chip · label + description · tags (New / Changed, source) · ⋯ menu (Show rule text, Update from the assistant, Remove).
  • Change stripes: 3 px inset left edge: green added, orange changed, red removed (removed rows also strike the name).
  • Diff: “Same as live so far” until something changes, then added / removed / changed chips.
  • Checks: bordered list, one line each; badge “n to fix” (orange, red if blocking) or “All good”. Rows for an assistant carry an Add / Update link.
  • Footer: Test this version (left) · Cancel · Publish. Label becomes “Publish and start trial” in Enforce.
4

Builder · starter rules

Allows exactly what each assistant uses today. Every governed assistant is pre-selected when starting the first version.

  • Sub-header pattern used by every sub-view: 32 bordered back button, title 16/24, one-line caption.
  • Assistant list: checkbox 16, name 14/20 medium, inventory caption, status chip right: Included green · Update available orange · Not included grey.
  • Not-governed assistants are listed disabled at 55% opacity with a “Not governed yet” chip.
  • “Show rule text” disclosure reveals the generated text in a mono code block. Add to version is right-aligned.
5

Builder · from a template

Four equal tiles; the chosen one opens one form panel with fields, a live preview and Add to version.

  • Tiles: 64 tall, 4 per row, gap 8, 28 icon well tinted green (allow) or red (block); selected = blue border + inset ring + selected fill.
  • Form panel: padding 20, gap 16, radius 12, --gv-nested fill; template title + description first.
  • Multi-select trigger: min 40; pills 26 tall, mono 12, blue tint, each with an 18 × remove button; caret rotates 180° when open.
  • Menu: search (32) + “n of N selected” + Select all / Clear all; list max 220 then scrolls; options show checkbox, mono name and who uses it (tools) or the provider (models).
  • Clicking an option keeps the menu open; clicking outside closes it; × on a pill removes without opening.
  • Preview: the exact rule row that will be added; a quiet note replaces it while a required value is missing.
  • Rule name defaults to an unused name (refund-limit-2…) because template default names repeat.
6

Builder · write a rule

For advanced users. Check runs the parser without saving; errors appear under the editor.

  • Mono textarea 12/18, min-height 220, spell-check off; starts with a commented example.
  • Hint: “Start every rule with @id("my-rule") so the activity log can tell you which rule decided.”
  • Parse error (422 invalid_policy) shows in --text-coloured-red under the editor; Add to version stays enabled but refuses invalid text.
  • A duplicate rule name is refused at Add with “Rule name … is already used. Rename it.”
7

Version details drawer

Opens from any version row. Actions depend on the version’s status and the workspace mode.

  • Drawer 520 × full height, right edge, scrim behind; header 16 padding with status chip and close.
  • Sections divided by --strokes-line-3, padding 16: Reason · Compared with the live rules (diff rows) · n rules · Rules check · Show rule text.
  • Footer right-aligned buttons, small (32).
  • Trial note in a blue inline box: “On trial since …; it can go live after …”.
8

Confirm dialogs

Every lifecycle action asks for a reason and repeats the rules check. A version that allows nothing needs an extra “I understand” tick.

  • Reason: required, 1–2000 characters, counter “n / 2000” in mono 11; primary button disabled until filled.
  • Stop trial uses the danger button (--red-600). Errors that the admin can fix stay inline in a red box; the dialog stays open.
9

Toasts

Bottom-centre, max two stacked, auto-dismiss after about 4 seconds.

Keyboard & accessibility

Esc closes the open menu, then the dialog, then the drawer. The multi-select trigger is role="button" and opens with Enter or Space; options are role="option" with aria-selected. Focus ring: 2 px --strokes-type-focus. Every status uses an icon plus a word.

All under /governance/v1; scope key workspace:<id without hyphens> in the path. Every write sends reason; pass timeout: 15000; invalidate ['gov', scope] after success.
