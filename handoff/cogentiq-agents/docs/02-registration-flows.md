# Registering a remote agent

A remote agent is one that runs outside Cogentiq. Registering it means
ending up holding **one A2A Agent Card** — an address, a credential and
a set of skills. The three routes differ only in where that card comes
from:

| Route | `wiz.proto` | The card comes from | Step 3 asks for |
| --- | --- | --- | --- |
| **Connect it directly** *(default)* | `direct` | an integration already registered in the workspace | nothing — review only |
| **It is already an agent** | `a2a` | a card published by an A2A server | which card, and how to authenticate to it |
| **It is a plain API** | `rest` | generated by the managed adapter from an uploaded OpenAPI document | nothing — review only |

Only one card per agent, everywhere. To combine several, register them
separately and compose them in an orchestrator.

---

## The shape of the modal

Three steps — **Details → Connection → Review** — in a 560px card with a
fixed header, a segmented stepper, a scrolling body and a footer.

- The stepper moves **backwards only**. Clicking an earlier step returns
  to it; clicking a later one is ignored, because it has nothing to show
  until the step before it is answered.
- **Continue** carries `aria-disabled` while the step is unanswered and
  the reason sits beside it as a hint (`stepHint()`). Clicking it anyway
  toasts the same hint rather than doing nothing silently.
- Each step opens scrolled to its own top.
- Escape and the X close the modal; there is no "are you sure".
- Registration is not activation. The agent enters governance review, and
  a note under the footer says so.

## Step 1 · Details

Two fields: **Agent name** (required) and **Description** (optional).
Nothing else — the description defaults from the card when left blank,
so asking for more here would be asking twice.

**Continue when:** the name is non-empty after trimming.

---

## Step 2 · Connection

Three choice cards, single select, `Connect it directly` selected by
default. Each is an icon tile, a title, one line of subtext and a radio.
Choosing one swaps the group below it — the rest of the step is whatever
that route needs.

### Route A · Connect it directly

One dropdown: **Integration**. Closed it shows the value and a chevron;
open it lists the registered integrations as icon + name + description,
with **New integration** as the last row. That button appears only while
the list is open — closed, the control is just the value and a chevron.

An integration *is* one agent card — an address, a credential and the
shape of the call, registered once and reused. Creating one opens a
nested modal (`#intScrim`) over the dimmed wizard:

| Field | Required | Notes |
| --- | --- | --- |
| Name | ✓ | what it is called in the list |
| Base URL | ✓ | `https://…` |
| Description | | shows under the name in the list |
| Authentication | ✓ | Bearer token · API key · OAuth 2.0 · Basic · mTLS · None; the credential fields below it change with the choice |
| Request method + path | ✓ | e.g. `POST` `/v1/score` |
| Message field | | JSONPath where the prompt goes; defaults to `$.query` |
| Response field | | JSONPath the answer comes back in; defaults to `$.answer` |
| Timeout | | seconds, defaults to 60 |

Save is gated on name, base URL and path, each with its own message
("Give the request a path."). The saved integration takes a slug of its
name as its single skill id, is prepended to the list, and becomes the
picker's answer straight away — you never have to find what you just
made.

Workspace ID and permissions are deliberately **not** here — they belong
to the workspace, not the connection.

**Continue when:** an integration is selected.

### Route B · It is already an agent

One dropdown: **A2A server**, listing the servers already known, each
with its host and how many cards it publishes, plus **Register a new
server** as the last row. Registering one takes a URL, discovers the
cards it publishes from `/.well-known/`, and lets you set the auth for
each discovered card there and then — the one moment somebody has the
server's own documentation open beside them.

**Continue when:** a server is selected.

### Route C · It is a plain API

An upload zone for an **OpenAPI spec or manifest**, plus a hint
explaining what happens: each operation becomes a skill, and the managed
adapter serves the document as an agent card, so nothing needs hosting.

On drop the file validates before the step can be left:

1. `checking` — spinner, "Checking the document…"
2. `ok` — green tick, `Valid OpenAPI 3.0.3 · 4 operations · https://api.weatherco.com/v2`
3. `error` — red, the parse error, and Continue stays disabled

In the prototype `takeSpec()` accepts any file and reports a fixed result
after 900ms. Real parsing replaces it; keep the three states.

**Continue when:** a file is uploaded **and** validation has returned ok.

## Step 3 · Review

The last step is named Review because two of the three routes have
nothing left to ask by then.

### Routes A and C — review only

In order, top to bottom:

1. **THE AGENT YOU ARE ADDING** — the agent card preview: mark, name,
   `Remote` badge, description, skill tags. 12px between the name row
   and the description (see the note at the end of this file).
2. **The Agent Card JSON** — what was received or generated, in a panel
   captioned with where it came from ("Built from the *Acme Claims Agent*
   integration" / "Generated by the managed adapter from
   *weatherco-openapi.json*") and a Copy button. Syntax coloured by
   token: keys cyan, strings green, numbers orange, booleans purple.
   The panel scrolls at `max-height: 260px`.
3. **The connection facts** — protocol, integration or server, endpoint,
   request shape, auth.

There is no `In review` badge on the preview. Registration always enters
review, and the note under the footer already says so.

### Route B — choose the card, then authenticate

1. **AGENT CARD** — a dropdown of the cards the chosen server publishes,
   single select, each row showing name, description and skill count.
2. **AUTHENTICATION** — the method for *this card*, as a segmented
   control, with the matching credential fields under it:

   | Method | Fields |
   | --- | --- |
   | Bearer token | token |
   | API key | header name (defaults `X-API-Key`) + key |
   | OAuth 2.0 | client id + client secret |
   | Basic | username + password |
   | mTLS | client certificate |
   | None | — |

3. **THE CARD WE FETCHED** — the same JSON panel, captioned with the
   `.well-known` URL it came from. It appears **only once a card is
   chosen and the credentials are filled**, because until then there is
   nothing to have fetched.

No agent preview on this route: the card being chosen and authenticated
*is* the subject of the step, and showing it twice read as two things.

**Register when:** routes A and C — always; route B — a card is selected
and `cardAuthOK()` passes.

---

## After Register

`createRemote()` does all of this:

- prepends the new agent to the list with `state: 'review'`
- resets the filters to In workspace → Remote so the new agent is on
  screen, and clears search
- opens the detail drawer on it
- toasts `<name> registered — awaiting governance approval.`

## One function to read first

`draft()` in `02-app.js` returns the agent the wizard would create, as it
currently stands. The preview, the review rows and the registration all
read it, so what the last step shows and what gets created cannot drift
apart. If you change what an agent is, change it there.

| Function | Does |
| --- | --- |
| `draft()` | the agent as currently specified |
| `cardJSON()` | the A2A Agent Card for the current route |
| `paintWiz()` | single render pass — step visibility, validity, button state |
| `stepOK()` / `stepHint()` | whether the step is answered, and what to say if not |
| `cardAuthOK()` | whether the credential for the chosen auth method is filled |
| `takeSpec()` | the upload + validation stub |
| `createRemote()` | commit, then land the user on the result |

### Conditional fields

Three attribute patterns drive show/hide, all resolved in one pass:

```html
<div data-only="direct">        <!-- shown when wiz.proto === 'direct'   -->
<div data-cauth-only="bearer">  <!-- shown when wiz.cardAuth === 'bearer' -->
<div data-niauth-only="apikey"> <!-- shown when wiz.niAuth === 'apikey'   -->
```

Each has a paired CSS rule so `[hidden]` beats the element's own
`display`. Adding a case means adding markup only.

### Wizard state

```js
const wiz = {
  step: 1,               // 1 · 2 · 3
  proto: 'direct',       // 'direct' | 'a2a' | 'rest'
  srvId: null,           // chosen A2A server
  integId: null,         // chosen integration
  pick: null,            // chosen agent card name (a2a only)
  cardAuth: 'bearer',    // auth method for that card
  niAuth: 'bearer',      // auth method inside the New integration modal
  restFile: null,        // { name, state: 'checking' | 'ok' | 'error' }
  restOk: false,
  integOpen: false, csOpen: false, regOpen: false   // dropdown open states
};
```

## A note on the 12px in the preview card

The Figma frames space the name and the description 12px apart, measured
between the text bounding boxes as Figma does it. Implemented literally
in CSS that reads as ~19px, because each line also carries half its
leading as empty space — 4px under a 16/24 name, 3px over a 14/20
description.

The prototype trims that back so the visible gap is the 12px the design
means:

```css
.ag-prev__id  { display: flex; flex-direction: column; gap: 12px; }
.ag-prev__top { margin-bottom: calc((var(--fs-body-2) - var(--lh-body-2)) / 2); }  /* -4px */
.ag-prev__desc { margin: calc((var(--fs-body-3) - var(--lh-body-3)) / 2) 0; }      /* -3px */
```

Keep the trim, or the card comes out looser than the design.
