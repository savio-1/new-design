Behaviour

  • Esc closes the top layer onlyOrder: New integration modal, then the “Which connection method?” sheet, then the wizard. Open popovers and the Create menu close first and return focus to their trigger.
  • Scrim click closesClicking the dimmed area outside a modal closes that modal. Clicks inside popovers stop propagation; any other click closes open popovers.
  • Step tabs go backwards onlyDetails / Connection / Review are tabs, but only earlier steps are clickable. Forward movement is Continue. Each step opens scrolled to its top. The last step's primary button reads “Register agent”.
  • Reopening the wizard resets itEvery field, selection and uploaded document is cleared; the route resets to Connect directly.
  • Changing an upstream choice clears downstream onesSwitching route, server or integration clears the selected agent card. Removing the API document clears its validation.
  • The card decides its auth defaultPicking an agent card preselects the auth type the card declares (for example “API key (Bearer)” selects API key), so the badge and the radio never disagree.
  • Card JSON appears only once it could be fetchedOn step 3 (A2A) the Agent Card document is shown after a card is picked and its credential is filled, labelled “Fetched from {server}{card path}”, with Copy.
  • Registering a server happens in place“Register a new server” at the foot of the server list opens an inline form: name, URL, Discover agent cards. Each discovered card shows its path and an editable auth select. Register server adds it to the top of the list and selects it.
  • New integration sits over the wizardCreating one keeps the half-filled wizard behind it. On save the integration is added to the top of the list and becomes the selection.
  • API document validationAccepts JSON or YAML by drop, browse or “Use a sample spec instead”. Shows a spinner and “Validating…”, then “Valid OpenAPI 3.0.3 · 4 operations · {url}” or the error “Could not read this file — expected OpenAPI 3.x or an agent manifest.” The prototype always succeeds after 0.9 s.
  • After Register agentThe wizard closes, filters reset to In workspace + Type Remote, the new agent is first in the list with status In review and Created by You, its detail panel opens, and the toast confirms.
  • Detail panel actions follow stateRun agent is primary. The secondary reads Edit for built agents, Connection for remote agents, and Preview in the Marketplace, where the primary becomes Add to workspace.
  • Platform railCrunched at 68 px, opens to 240 px on hover after 140 ms and closes 200 ms after leaving. It overlays the page; the page keeps a fixed 68 px gutter. One category is open at a time.
  • Card and table selectionSelecting an item marks it selected (blue border on cards, tinted row with a 3 px inset bar in the table) and opens the panel. Search, filter or source changes clear the selection and close the panel.

Data model

The shapes the prototype renders from, written as TypeScript. Field names match the prototype source so the two can be read side by side.

type AgentType  = 'agent' | 'orchestrator' | 'remote';
type AgentState = 'running' | 'idle' | 'review' | 'error' | 'draft';
//   labels:      Running   Idle    In review  Failing  Draft

interface Agent {
  name: string;
  type: AgentType;
  state: AgentState;
  desc: string;
  by: string;              // creator or publisher
  tags: string[];
  updated: string;         // relative, e.g. "4h ago"
  runs: number;            // last 30 days
  usedBy: { name: string; kind: 'automation' | 'assistant' }[];
  problem?: string;        // shown as NEEDS ATTENTION

  // built agents and orchestrators
  model?: string;          // '—' when not configured
  tools?: string[];
  skills?: string[];
  guards?: string[];       // guardrails
  parent?: string;         // orchestrated by
  members?: { name: string; role: string; remote: boolean }[];

  // marketplace only
  installs?: number;
}
type Connection = 'a2a' | 'direct' | 'rest';

interface RemoteAgent extends Agent {
  type: 'remote';
  conn: Connection;
  endpoint: string;        // host + path, no scheme
  server: string;          // A2A server, integration,
                           // or "Cogentiq Managed A2A"
  auth: string;            // human label
  cards: string[];         // agent card names
  agentSkills: string[];   // skill ids, e.g. fraud.score

  // direct only
  reqMethod?: 'POST' | 'GET' | 'PUT' | 'PATCH';
  reqPath?: string;
  msgField?: string;       // JSON path, e.g. $.query
  respField?: string;      // JSON path, e.g. $.answer
  ctxField?: string;       // session field, optional
}

// A newly registered agent always starts as
// { state: 'review', by: 'You', runs: 0, tags: [] }
interface A2AServer {
  id: string;
  name: string;            // "Acme Bank A2A"
  url: string;             // no scheme
  updated: string;
  managed?: boolean;       // Cogentiq Managed A2A
  cards: AgentCardRef[];
}

interface AgentCardRef {
  name: string;
  desc: string;
  skills: string[];
  auth: 'API key (Bearer)' | 'OAuth 2.0' | 'mTLS'
      | 'Basic auth' | 'None';
  path: string;            // /.well-known/agents/<slug>.json
}
interface Integration {
  id: string;
  name: string;
  url: string;             // base URL, with scheme
  desc: string;
  auth: string;            // Bearer token, API key, ...
  timeout: number;         // seconds, default 60
  skills: string[];        // one skill, slug of name
  method: 'POST' | 'GET' | 'PUT' | 'PATCH';
  path: string;
  msg: string;             // message JSON path
  resp: string;            // response JSON path
}

type AuthKey = 'apikey' | 'basic' | 'bearer'
             | 'oauth' | 'mtls' | 'none';

Open questions

Things the prototype leaves open or stubs. Settle these with design before building.

  1. Direct route names the card after the integrationThe step 1 name becomes the agent's name, but the Agent Card's name and the panel's Skill row use the integration name (Acme Claims Agent). Should the card take the agent's name?
  2. Where auth for an A2A card is definedAuth is set per card twice: when registering a server (“stored with the server and used on every call”) and again on step 3 with the credential. Which one is the source of truth, and is the step 3 value scoped to this agent or to the card?
  3. “API key (Bearer)”Server cards declare “API key (Bearer)”, which maps to the API key option with an X-API-Key header, not to Bearer Token. Confirm the mapping, or split the label.
  4. No preview on step 3 for A2ADirect and Plain API show “The agent you are adding”; the A2A route shows only the card picker, credential and fetched JSON. The source says this is deliberate. Confirm.
  5. Stubs to replaceDiscovery returns a fixed list of four cards for any URL. Spec validation always passes and reads 4 operations. Run, Edit, Connection, the ⋯ menu (Duplicate · Export · Archive) and the agent and orchestrator builders are toasts.
  6. Credential checks in New integrationThe modal requires name, URL and path, but not the fields of the chosen auth type, and stores only the auth label. Should it block like step 3 does?
  7. Description fallbackWhen the description is left blank, A2A uses the card's description, Direct the integration's, and Plain API a generated sentence. Confirm this is wanted rather than requiring one.
